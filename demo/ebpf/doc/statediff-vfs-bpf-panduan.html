0Gambaran Besar

File ini berisi satu program BPF yang dimuat ke dalam kernel Linux. Isinya adalah kumpulan hook: potongan kode yang dijalankan kernel setiap kali fungsi VFS tertentu dipanggil (mis. vfs_mkdir, vfs_write). Setiap operasi filesystem yang relevan (buat file, tulis, hapus, rename, dst) punya sepasang hook: satu di titik masuk fungsi kernel, satu di titik keluar-nya.

Alur besar setiap operasi selalu mengikuti pola yang sama:

1. syscall dipanggil user (mkdir, write, rename, ...) 2. kernel menjalankan fungsi VFS terkait (vfs_mkdir, vfs_write, ...) | |-- hook MASUK: cek apakah objek ini sedang diawasi, | simpan data mentah ke map "pending_*" | fungsi VFS benar-benar berjalan (buat direktori, tulis byte, dst) | |-- hook KELUAR: ambil data dari "pending_*", cek hasilnya sukses, | bentuk event final, kirim ke ring buffer "rb" v 3. program userspace (statediff_vfs.c, file berikutnya) membaca ring buffer

Dokumen ini menelusuri file dari yang paling dasar (map, struct) ke yang paling kompleks (penulisan vectored, native AIO), supaya setiap hook bisa dipahami sebagai variasi dari pola yang sama.

1.1Apa itu BPF map

statediff_vfs.bpf.c · baris 81–86
struct {
	__uint(type, BPF_MAP_TYPE_HASH);
	__uint(max_entries, 65536);
	__type(key, struct statediff_vfs_inode_key);
	__type(value, unsigned char);
} tracked_dirs SEC(".maps");
Penjelasan

Ini bukan struct C biasa untuk membuat variabel lokal. Ini adalah definisi tabel yang dibaca oleh loader BPF (libbpf) untuk membuat tabel key-value di dalam kernel, sebelum program BPF dimuat.

  • __uint(type, BPF_MAP_TYPE_HASH) — jenis tabelnya hash map: satu key unik memetakan ke satu value.
  • __uint(max_entries, 65536) — kapasitas maksimum tabel.
  • __type(key, ...) / __type(value, ...) — tipe data key dan value.
  • SEC(".maps") — menandai struct ini ke compiler BPF supaya diletakkan di section ELF .maps. Ini yang membuat loader tahu "ini definisi map", bukan variabel biasa.

Map bisa dibaca/ditulis dari dua sisi: (1) dari dalam program BPF lewat bpf_map_lookup_elem() / bpf_map_update_elem(), dan (2) dari program userspace lewat libbpf.

Contoh isi tabel tracked_dirs 
key = {dev: 64768, ino: 100}   ->  value = 1   // "/tracked/dir"

Value-nya (unsigned char) selalu diisi 1 dan tidak pernah dibaca isinya — yang dicek hanya apakah key-nya ada di tabel. Semua map "daftar keanggotaan" di file ini (tracked_dirs, mmap_files, dio_inflight) memakai pola ini.

Penjelasan

SEC("fentry/vfs_mkdir") menempelkan fungsi handle_vfs_mkdir ke titik masuk fungsi kernel vfs_mkdir(). Kernel menjalankan fungsi ini setiap kali vfs_mkdir() dipanggil, sebelum isi vfs_mkdir() sendiri dieksekusi. Parameter yang diterima (idmap, dir, dentry, mode) persis sama dengan parameter asli vfs_mkdir() di kernel — BPF meneruskannya apa adanya.

SEC("fexit/vfs_mkdir") menempel di titik keluar — dijalankan tepat setelah vfs_mkdir() selesai (return), sebelum kontrol kembali ke pemanggilnya. Parameternya sama seperti versi fentry, ditambah satu parameter di akhir: ret — nilai balik fungsi aslinya (0 = sukses, negatif = kode error).

BPF_PROG(...) adalah macro dari libbpf yang membungkus detail teknis pemanggilan trampoline BTF, supaya fungsi bisa ditulis dengan tanda tangan (signature) normal seperti fungsi C biasa.

Kenapa harus berpasangan?

Sebagian data (misalnya "apakah operasi berhasil") hanya tersedia di titik keluar. Sebagian lain (misalnya "siapa direktori induknya sebelum operasi berjalan") lebih murah diambil di titik masuk. Karena itu data dari fentry perlu "dititipkan" agar bisa dipakai lagi oleh fexit — inilah fungsi map pending_* yang dibahas di bagian 2.2 dan 5.

1.3Hook kprobe / kretprobe

int BPF_KPROBE(handle_vfs_writev, struct file *file, const struct iovec *vec,
	       unsigned long vlen, loff_t *pos)

SEC("kretprobe/vfs_writev")
int BPF_KRETPROBE(handle_vfs_writev_ret, ssize_t ret)
Penjelasan

fentry/fexit butuh informasi tipe (BTF) yang lengkap dan hanya bisa menempel ke fungsi yang benar-benar berdiri sendiri sebagai simbol kernel. Untuk vfs_writev, komentar sumber di baris 755–765 menjelaskan bahwa jalur pemanggilan sebenarnya (do_writev → vfs_writev → do_iter_write) sebagian besar sudah di-inline compiler, dan vfs_writev adalah satu-satunya simbol dari jalur itu yang masih bisa ditempeli hook secara andal — di sini lewat mekanisme yang lebih tua dan lebih generik, yaitu kprobe/kretprobe (menempel ke alamat instruksi mana pun yang punya simbol di kallsyms, tidak butuh BTF trampoline).

Konsekuensi pentingnya ada pada BPF_KRETPROBE: fungsi ini hanya menerima ret. Tidak ada file, vec, atau pos lagi — di titik kembali fungsi, register CPU sudah berisi nilai balik, bukan argumen asli. Karena itu handle_vfs_writev (bagian masuk) wajib menyimpan pointer vec dan pos ke map pending_writev terlebih dulu, supaya handle_vfs_writev_ret bisa membacanya kembali secara manual (lihat bagian 8.2).

1.4Ring buffer & BPF_CORE_READ

statediff_vfs.bpf.c · baris 76–79
struct {
	__uint(type, BPF_MAP_TYPE_RINGBUF);
	__uint(max_entries, 64 * 1024 * 1024);
} rb SEC(".maps");
Penjelasan

Map rb adalah map bertipe khusus, BPF_MAP_TYPE_RINGBUF: sebuah buffer melingkar 64 MiB. Ini adalah satu-satunya jalur keluar data dari program BPF ke userspace di file ini. Program BPF menulis lewat bpf_ringbuf_reserve() + bpf_ringbuf_submit() (memesan slot berukuran tetap lalu mengisinya) atau bpf_ringbuf_output() (menyalin buffer langsung, dipakai untuk data berukuran variabel seperti isi tulisan file). Userspace membacanya lewat polling (dibahas di file statediff_vfs.c).

Satu detail teknis lain yang muncul berulang di seluruh file adalah BPF_CORE_READ(struct_ptr, field). Ini pengganti wajib untuk akses langsung seperti struct_ptr->field. Program BPF tidak boleh membaca memory kernel secara langsung karena verifier BPF (bagian kernel yang memeriksa keamanan program BPF sebelum dijalankan) harus bisa memastikan setiap akses memory valid. BPF_CORE_READ juga menangani CO-RE (Compile Once – Run Everywhere): posisi field yang sebenarnya di dalam struct kernel bisa berbeda antar versi kernel, dan BPF_CORE_READ menyesuaikannya otomatis saat program dimuat, sehingga satu file .o hasil kompilasi bisa jalan di kernel versi lain tanpa dikompilasi ulang.

STATEDIFF_VFS_EVENT_FIELDS adalah macro C preprocessor: daftar field yang disisipkan mentah-mentah ke dua struct berbeda, supaya tidak perlu menulis field yang sama dua kali. Kenapa key-nya pid_tgid untuk semua map pending_*?

Hook masuk dan hook keluar dari satu operasi yang sama berjalan berurutan di thread kernel yang sama — tidak ada operasi lain dari thread itu yang menyela di antaranya. pid_tgid (dijelaskan di Bagian 5.1) karena itu cukup sebagai kunci untuk mencocokkan draft data dari entry ke exit hook miliknya sendiri.

Kenapa scratch beda dari event_scratch?

scratch pakai PERCPU_ARRAY karena tipe map ini punya batas ukuran per elemen 32 KiB — cukup untuk statediff_vfs_pending (kecil). event_scratch perlu menampung statediff_vfs_event_storage yang berukuran ~4 MiB, jauh melebihi batas itu, sehingga harus memakai ARRAY biasa yang di-index manual dengan ID CPU (bpf_get_smp_processor_id()) untuk meniru perilaku "satu slot per CPU" tanpa kena batas ukuran.

4.1Helper: dari inode/dentry ke identitas

statediff_vfs.bpf.c · baris 346–385
static __always_inline int inode_to_key(struct inode *inode,
					struct statediff_vfs_inode_key *key)
{
	struct super_block *sb;

	if (!inode)
		return 0;

	sb = BPF_CORE_READ(inode, i_sb);
	if (!sb)
		return 0;

	key->ino = BPF_CORE_READ(inode, i_ino);
	key->dev = BPF_CORE_READ(sb, s_dev);
	return key->ino != 0;
}

static __always_inline int dentry_to_key(struct dentry *dentry,
					 struct statediff_vfs_inode_key *key)
{
	struct inode *inode;

	if (!dentry)
		return 0;
	inode = BPF_CORE_READ(dentry, d_inode);
	return inode_to_key(inode, key);
}

static __always_inline int dentry_parent_key(struct dentry *dentry,
					     struct statediff_vfs_inode_key *key)
{
	struct dentry *parent;

	if (!dentry)
		return 0;
	parent = BPF_CORE_READ(dentry, d_parent);
	if (!parent)
		return 0;
	return dentry_to_key(parent, key);
}
Penjelasan

inode_to_key — membaca inode->i_sb (superblock, mewakili filesystem/mount tempat inode berada), lalu mengisi key->ino dari inode->i_ino dan key->dev dari sb->s_dev. Mengembalikan 1 kalau ino berhasil dibaca dan bukan nol.

dentry_to_key — struct dentry merepresentasikan satu entri nama di dalam sebuah direktori: pasangan nama string dan inode yang ditunjuknya. Fungsi ini membaca dentry->d_inode (inode yang ditunjuk entri ini), lalu memanggil inode_to_key di atasnya.

dentry_parent_key — membaca dentry->d_parent (dentry dari direktori yang memuat dentry ini), lalu memanggil dentry_to_key pada parent tersebut. Dipakai setiap kali hook perlu tahu identitas direktori induk dari objek yang sedang dioperasikan.

Contoh konkret 
Struktur: /tracked/dir/photos  (photos adalah subdirektori, ino=205)
          /tracked/dir           (ino=100, dev=64768)

dentry_to_key(dentry photos)      -> key = {dev:64768, ino:205}
dentry_parent_key(dentry photos)  -> key = {dev:64768, ino:100}

4.2Helper: nama & tipe objek

statediff_vfs.bpf.c · baris 417–431
static __always_inline int read_dentry_name(struct dentry *dentry, char *name)
{
	struct qstr q = {};
	long n;

	if (!dentry)
		return 0;

	BPF_CORE_READ_INTO(&q, dentry, d_name);
	if (!q.name || !q.len || q.len >= STATEDIFF_VFS_NAME_LEN)
		return 0;

	n = bpf_probe_read_kernel_str(name, STATEDIFF_VFS_NAME_LEN, q.name);
	return n > 1 && n <= STATEDIFF_VFS_NAME_LEN;
}
Penjelasan

dentry->d_name bertipe struct qstr: sebuah pointer ke karakter (name) plus panjangnya (len) — bukan string C biasa yang selalu diakhiri \0. BPF_CORE_READ_INTO(&q, dentry, d_name) menyalin seluruh struct qstr itu ke variabel lokal q.

Baris if (!q.name || !q.len || q.len >= STATEDIFF_VFS_NAME_LEN) menolak nama kosong atau nama yang melebihi kapasitas buffer tujuan (256 byte).

bpf_probe_read_kernel_str menyalin string dari alamat q.name (memory kernel) ke buffer name milik pemanggil, sekaligus memastikan hasilnya diakhiri \0 dengan aman. Nilai baliknya adalah jumlah byte yang disalin termasuk terminator.

5.1current_key & filtered_out

statediff_vfs.bpf.c · baris 290–307
static __always_inline unsigned long long current_key(void)
{
	return bpf_get_current_pid_tgid();
}

static __always_inline int filtered_out(void)
{
	unsigned long long pid_tgid = bpf_get_current_pid_tgid();

	if (ignored_pid && (unsigned int)(pid_tgid >> 32) == ignored_pid)
		return 1;
	return 0;
}
Penjelasan

bpf_get_current_pid_tgid() adalah helper BPF yang mengembalikan satu nilai 64-bit: 32 bit atas berisi PID (thread group ID / ID proses), 32 bit bawah berisi TID (ID thread individual). Nilai gabungan ini dipakai sebagai key semua map pending_*.

filtered_out mengambil 32 bit atas (pid_tgid >> 32, yaitu PID) dan membandingkannya dengan ignored_pid — variabel global yang diisi userspace sebelum program dimuat, berisi PID dari proses capturer itu sendiri (lihat baris 203: const volatile unsigned int ignored_pid = 0;). Ini satu-satunya filter "menyeluruh" di file ini: mencegah aktivitas filesystem milik capturer sendiri (mis. saat men-scan tree di awal) ikut terekam.

Contoh konkret 
Proses capturer berjalan dengan PID = 9001 -> ignored_pid = 9001
Proses lain (mis. bash menjalankan `mkdir`) punya PID = 4210

filtered_out() saat dipanggil dari proses PID 4210 -> 0 (tidak difilter)
filtered_out() saat dipanggil dari proses PID 9001 -> 1 (difilter, capture dihentikan)

	/* ... reset field key lain dengan pola sama ... */
	p->name[0] = '\0';
	p->new_name[0] = '\0';
}

static __always_inline struct statediff_vfs_pending *get_scratch(unsigned int op)
{
	unsigned int key = 0;
	struct statediff_vfs_pending *p;

	p = bpf_map_lookup_elem(&scratch, &key);
	if (!p)
		return 0;
	init_pending(p, op);
	return p;
}
Penjelasan

get_scratch mengambil satu-satunya slot di map scratch (map PERCPU_ARRAY dengan max_entries = 1, jadi key selalu 0) — karena tipenya per-CPU, setiap CPU sebenarnya punya salinan sendiri-sendiri, sehingga dua hook yang berjalan bersamaan di CPU berbeda tidak akan saling menimpa slot ini.

Sebelum dikembalikan, slot itu dibersihkan lewat init_pending supaya tidak membawa sisa data dari pemakaian sebelumnya di CPU yang sama.

Kenapa tidak langsung deklarasi struct statediff_vfs_pending p; di dalam fungsi hook?

Verifier BPF membatasi ukuran stack (512 byte). statediff_vfs_pending berisi dua buffer nama 256 byte plus beberapa field lain — terlalu besar untuk stack. Map scratch dipakai sebagai "ruang kerja" di luar stack untuk menghindari batas ini.

5.3fill_common: dari pending ke event

statediff_vfs.bpf.c · baris 433–460
static __always_inline void fill_common(struct statediff_vfs_event *e,
					const struct statediff_vfs_pending *p,
					long long ret)
{
	unsigned long long pid_tgid = bpf_get_current_pid_tgid();
	unsigned long long uid_gid = bpf_get_current_uid_gid();

	e->op = p->op;
	e->pid = pid_tgid >> 32;
	e->tid = (unsigned int)pid_tgid;
	e->uid = (unsigned int)uid_gid;
	e->gid = uid_gid >> 32;
	e->cgroup_id = bpf_get_current_cgroup_id();
	e->ret = ret;
	e->mode = p->mode;
	e->flags = p->flags;
	e->offset = p->offset;
	e->size = p->size;
	e->cookie = 0;
	e->is_dir = p->is_dir;
	e->data_len = 0;
	e->parent = p->parent;
	e->object = p->object;
	e->new_parent = p->new_parent;
	e->new_object = p->new_object;
	__builtin_memcpy(e->name, p->name, sizeof(e->name));
	__builtin_memcpy(e->new_name, p->new_name, sizeof(e->new_name));
}
Penjelasan

Ini adalah fungsi yang benar-benar mengubah draft statediff_vfs_pending (p) menjadi event final statediff_vfs_event (e), dipanggil oleh hampir semua hook keluar. Field yang disalin apa adanya dari p: op, mode, flags, offset, size, is_dir, parent, object, new_parent, new_object, name, new_name.

Field yang baru diisi di sini (tidak ada di pending): pid/tid dari bpf_get_current_pid_tgid(), uid/gid dari bpf_get_current_uid_gid() (pola bit yang sama: 32 bit atas dan bawah), cgroup_id dari bpf_get_current_cgroup_id(), dan ret — diteruskan sebagai parameter fungsi, bukan dibaca dari p, karena nilai ini datang dari hasil operasi kernel (parameter ret hook keluar), sesuatu yang tidak diketahui saat pending dibuat di hook masuk.

e->cookie = 0 dan e->data_len = 0 di-set default di sini; sebagian pemanggil (mis. jalur WRITE) mengubahnya lagi setelahnya.

5.4emit_pending_event: penyelesai bersama

statediff_vfs.bpf.c · baris 462–501
static __always_inline struct statediff_vfs_event *reserve_empty_event(void)
{
	return bpf_ringbuf_reserve(&rb, STATEDIFF_VFS_EVENT_HEADER_LEN, 0);
}

static __always_inline int emit_pending_event(void *map, long long ret)
{
	unsigned long long key = current_key();
	struct statediff_vfs_pending *p;
	struct statediff_vfs_event *e;

	p = bpf_map_lookup_elem(map, &key);
	if (!p)
		return 0;

	if (ret < 0) {
		bpf_map_delete_elem(map, &key);
		return 0;
	}

	e = reserve_empty_event();
	if (!e) {
		count_stat(11, 1);
		bpf_map_delete_elem(map, &key);
		return 0;
	}

	fill_common(e, p, ret);
	bpf_map_delete_elem(map, &key);
	count_stat(10, 1);
	bpf_ringbuf_submit(e, 0);
	return 0;
}
Penjelasan baris demi baris

reserve_empty_event() memanggil bpf_ringbuf_reserve(&rb, STATEDIFF_VFS_EVENT_HEADER_LEN, 0) — memesan slot di ring buffer rb sebesar header event saja (tanpa payload data[]), dan mengembalikan pointer langsung ke slot itu di dalam ring buffer. Dipakai oleh operasi yang tidak membawa data byte (mkdir, unlink, rmdir, dst).

emit_pending_event(map, ret) menerima map — pointer ke salah satu map pending_* (mis. &pending_mkdir) — dan ret, nilai balik operasi kernel dari hook keluar.

Baris p = bpf_map_lookup_elem(map, &key); mengambil draft yang tadi disimpan hook masuk, dengan key = current_key() (pid_tgid saat ini, Bagian 5.1). Jika tidak ketemu (mis. hook masuk sudah menghentikan proses lebih awal karena parent tidak tracked), fungsi berhenti tanpa efek.

Baris if (ret < 0) { ...; return 0; } — kalau operasi kernel gagal, draft dihapus dan tidak ada event dikirim sama sekali. File yang gagal dibuat, ditulis, dsb, memang tidak boleh masuk ke batch.

Baris e = reserve_empty_event(); memesan slot di ring buffer. Jika ring buffer penuh, reserve_empty_event mengembalikan NULL — kejadian ini dicatat lewat count_stat(11, 1) (menaikkan ringbuf_drops di map stats, Bagian 2.4/14) sebagai kehilangan data.

Baris fill_common(e, p, ret); — mengisi event dari draft, seperti dibahas Bagian 5.3.

Baris bpf_map_delete_elem(map, &key); — draft dibuang dari map pending_*, dilakukan sebelum submit supaya slot key ini bersih untuk pemakaian berikutnya oleh thread yang sama.

Baris bpf_ringbuf_submit(e, 0); — mengunci isi slot yang sudah diisi dan menandainya siap dibaca userspace. Ini titik akhir setiap hook keluar yang berhasil: dari sini, event sudah "keluar" dari program BPF.

5.5save_child_op: pembuka bersama

statediff_vfs.bpf.c · baris 503–536
static __always_inline int save_child_op(void *map, unsigned int op,
					 struct inode *dir,
					 struct dentry *dentry,
					 unsigned int mode)
{
	unsigned long long key = current_key();
	struct statediff_vfs_pending *p;

	count_enter(op);
	if (filtered_out())
		return 0;

	p = get_scratch(op);
	if (!p)
		return 0;
	if (!inode_to_key(dir, &p->parent))
		return 0;
	if (!dir_is_tracked(&p->parent)) {
		record_untracked_parent(op, &p->parent);
		return 0;
	}
	if (!read_dentry_name(dentry, p->name)) {
		count_stat(9, 1);
		return 0;
	}

	p->mode = mode;
	dentry_to_key(dentry, &p->object);
	p->is_dir = op == SD_VFS_OP_MKDIR || op == SD_VFS_OP_RMDIR ||
		dentry_is_dir(dentry);

	bpf_map_update_elem(map, &key, p, BPF_ANY);
	return 0;
}
Penjelasan baris demi baris

Parameter: map — map pending_* tujuan; op — jenis operasi; dir — inode direktori induk (argumen asli fungsi kernel yang di-hook); dentry — entri anak yang dioperasikan; mode — mode file, kalau relevan.

count_enter(op) — menaikkan counter "enter" sesuai op di map stats, dijalankan sebelum pengecekan lain, supaya statistik mencatat semua percobaan, bahkan yang nanti difilter.

if (filtered_out()) return 0; — berhenti kalau PID pemanggil adalah capturer sendiri (Bagian 5.1).

p = get_scratch(op); — ambil & bersihkan slot kerja (Bagian 5.2), langsung diisi op.

if (!inode_to_key(dir, &p->parent)) return 0; — ubah dir jadi identitas (dev, ino), simpan ke p->parent. Gagal (mis. dir NULL) → berhenti.

if (!dir_is_tracked(&p->parent)) { record_untracked_parent(...); return 0; } — titik keputusan scoping: kalau induknya bukan direktori yang diawasi, operasi ini bukan urusan capturer. record_untracked_parent mencatat statistik diagnostik (identitas parent yang tidak dikenal serta jenis op-nya) sebelum berhenti.

if (!read_dentry_name(dentry, p->name)) { count_stat(9, 1); return 0; } — ambil nama anak (Bagian 4.2). Gagal → naikkan counter name_read_fail, berhenti.

p->mode = mode; dentry_to_key(dentry, &p->object); — simpan mode, lalu identitas objek anak itu sendiri (kalau sudah punya inode).

p->is_dir = op == SD_VFS_OP_MKDIR || op == SD_VFS_OP_RMDIR || dentry_is_dir(dentry); — untuk mkdir/rmdir, objeknya pasti direktori secara definisi operasi (bahkan sebelum/sesudah inode-nya ada), jadi ditandai langsung tanpa mengecek inode; operasi lain (unlink) memakai hasil pengecekan dentry_is_dir yang sebenarnya.

bpf_map_update_elem(map, &key, p, BPF_ANY); — simpan draft yang sudah lengkap ke map pending_*, dengan key pid_tgid. BPF_ANY berarti "timpa kalau sudah ada entry dengan key ini, buat baru kalau belum ada".

Fungsi ini dipakai oleh hook masuk MKDIR, UNLINK, dan RMDIR — tiga operasi yang polanya identik: sebuah nama anak dihapus/dibuat di dalam direktori induk.

storage = get_event_scratch(); — ambil buffer staging 4 MiB milik CPU saat ini (Bagian 5.2). bpf_probe_read_user(storage->data, data_len, p->buf + emitted) — di sinilah isi byte tulisan benar-benar disalin, dari alamat user p->buf + emitted (Bagian offset dari buffer asli yang sudah dikirim ke emitted byte sebelumnya) ke buffer staging kernel. _user (bukan _kernel) dipakai karena buf memang alamat di memory proses user.

e->offset = start_offset + emitted; — setiap potongan event membawa offset file-nya sendiri, dihitung dari posisi awal tulisan ditambah berapa byte yang sudah dikirim di potongan-potongan sebelumnya.

bpf_ringbuf_output(&rb, storage, STATEDIFF_VFS_EVENT_HEADER_LEN + data_len, 0); — beda dari bpf_ringbuf_reserve+submit (Bagian 5.4) yang memberi pointer langsung ke slot ring buffer untuk diisi di tempat, bpf_ringbuf_output menyalin buffer storage yang sudah lengkap terisi ke ring buffer dalam satu langkah. Dipakai di sini karena data sudah harus dirakit dulu di event_scratch (empat MiB, tidak muat di stack), baru dipindah ke ring buffer.

Koreksi offset untuk O_APPEND

Untuk file yang dibuka dengan O_APPEND, posisi sebelum tulisan (dibaca hook masuk) belum tentu tempat byte itu benar-benar mendarat — kernel baru menggeser posisi file ke akhir selama operasi tulis berjalan. Kode (tidak ditampilkan di potongan atas demi ringkas) membaca ulang *pos di hook keluar dan menghitung mundur: start_offset = end_offset - ret, memakai posisi akhir yang sudah pasti benar dikurangi jumlah byte yang berhasil ditulis.

static long writev_emit_seg(unsigned int i, void *data)
{
	struct writev_emit_ctx *c = data;
	struct statediff_vfs_pending *p;
	const struct iovec *vec;
	struct iovec seg;

	p = bpf_map_lookup_elem(&pending_writev, &c->key);
	if (!p)
		return 1;

	vec = (const struct iovec *)p->iov_ptr;
	if (bpf_probe_read_user(&seg, sizeof(seg), &vec[i]) < 0) {
		count_stat(14, 1);
		return 1;
	}

	unsigned long long base = (unsigned long long)seg.iov_base;
	unsigned long long seg_len = (unsigned long long)seg.iov_len;
	if (seg_len == 0)
		return 0;

	unsigned int chunk = seg_len > STATEDIFF_VFS_MAX_WRITE_DATA_LEN
		? STATEDIFF_VFS_MAX_WRITE_DATA_LEN : (unsigned int)seg_len;

	struct statediff_vfs_event_storage *storage = get_event_scratch();
	struct statediff_vfs_event *e = (struct statediff_vfs_event *)storage;

	bpf_probe_read_user(storage->data, chunk, (const void *)base);

	fill_common(e, p, chunk);
	e->offset = p->offset + c->emitted;
	e->size = chunk;
	e->data_len = chunk;

	bpf_ringbuf_output(&rb, storage,
			   STATEDIFF_VFS_EVENT_HEADER_LEN + chunk, 0);
	c->emitted += chunk;
	return 0;
}
Penjelasan — apa itu bpf_loop?

bpf_loop(jumlah_iterasi, fungsi_callback, data, 0) adalah helper BPF yang menjalankan fungsi_callback berulang sebanyak jumlah_iterasi kali. Program BPF tidak boleh punya perulangan biasa (for/while) dengan jumlah iterasi yang tidak bisa dipastikan verifier di awal — bpf_loop adalah cara resmi untuk melakukan perulangan yang jumlahnya baru diketahui saat runtime.

i — nomor iterasi saat ini (indeks segmen iovec ke berapa). data — pointer ke struct writev_emit_ctx yang dibagikan ke semua iterasi, dipakai untuk melacak emitted (total byte yang sudah dikirim lintas-iterasi).

vec[i] dibaca lewat bpf_probe_read_user — array iovec ada di memory user, bukan kernel. Satu struct iovec berisi {iov_base, iov_len}: alamat & panjang satu segmen buffer.

Sisanya mengikuti pola yang identik dengan potongan vfs_write: baca isi segmen ke event_scratch, isi event, kirim ke ring buffer. Bedanya, offset filenya dihitung dari p->offset + c->emitted — c->emitted terakumulasi lintas-segmen (bukan lintas-chunk seperti pada vfs_write), karena tiap segmen iovec adalah tulisan yang letaknya berurutan begitu saja di file, mengikuti urutan segmennya.

Catatan verifier tentang emitted

Komentar sumber (baris 816–824) menekankan: emitted hanya boleh dipakai untuk mengisi nilai yang disimpan (e->offset), tidak pernah untuk menentukan alur kontrol (percabangan/pembatasan salinan). Kalau dipakai untuk itu, verifier BPF terpaksa melacak nilainya secara presisi di setiap iterasi dan mensimulasikan loop selangkah 4 MiB pada satu waktu — sampai batas jumlah langkah verifikasi terlampaui, dan program gagal dimuat sama sekali.

	fill_common(e, p, 0);
	bpf_ringbuf_submit(e, 0);
	return 0;
}
Penjelasan

Sebuah folio adalah satu (atau beberapa, untuk "large folio") halaman page-cache. Fungsi kernel __folio_start_writeback dipanggil setiap kali sebuah folio dirty (kotor, ada perubahan yang belum ditulis ke disk) mulai ditulis balik ke penyimpanan — ini titik pertemuan untuk semua jalur yang mengotori page cache, termasuk mmap store, bukan hanya write biasa.

mapping = BPF_CORE_READ(folio, mapping); if (!mapping || ((unsigned long)mapping & PAGE_MAPPING_FLAGS)) return 0; — beberapa bit rendah dari pointer mapping dipakai kernel sebagai flag penanda (mis. folio anonim, bukan milik file); baris ini menyaring folio yang bukan bagian dari sebuah file.

host = BPF_CORE_READ(mapping, host); — inode pemilik page cache ini. if (!bpf_map_lookup_elem(&mmap_files, &key)) return 0; — hanya diproses lebih lanjut kalau inode ini ada di mmap_files, yaitu file yang benar-benar sedang punya writable mmap aktif (didaftarkan oleh hook di atas). Ini yang membuat hook ini tidak "berisik" — mayoritas writeback di sistem sama sekali tidak menyentuh file yang diawasi lewat mmap.

p->offset = folio->index << PAGE_SHIFT; — folio->index adalah nomor halaman (bukan byte) di dalam file; digeser PAGE_SHIFT (12, artinya kali 4096) untuk mengubahnya jadi offset byte.

Event yang dikirim tidak membawa data byte sama sekali — hanya {object (inode), offset, size}. Komentar sumber (baris 1287–1295) menjelaskan userspace-lah yang nantinya memanggil pread() pada page cache di rentang ini untuk mengambil isi sebenarnya, pada saat capture (bukan saat writeback ini terjadi) — ditelusuri lebih lanjut di file statediff_vfs.c.

13Native AIO / DIO — io_submit_one + aio_complete_rw

Jalur paling rumit di file ini. InnoDB (MySQL) dan aplikasi libaio lain menulis lewat io_submit(IOCB_CMD_PWRITE), jalur kernel yang sama sekali tidak menyentuh vfs_write/vfs_writev.

Kenapa dua hook terpisah yang harus dipasangkan manual?

Titik hook yang "jelas" (aio_write) tidak bisa dipakai: fungsi ini di-inline compiler ke pemanggilnya, sehingga simbol keluarannya tidak pernah benar-benar dieksekusi sebagai fungsi berdiri sendiri (komentar sumber baris 1347–1352). Sebagai gantinya dipakai io_submit_one (submit, generik untuk semua filesystem) dan aio_complete_rw (completion). Keduanya dipasangkan lewat sebuah cookie: alamat struct iocb milik user, karena tidak ada pointer kiocb kernel yang tersedia di titik submit (dialokasikan belakangan) maupun struct file* yang tersedia di titik completion (hanya kiocb).

fexit/io_submit_one
statediff_vfs.bpf.c · baris 1565–1641 (dipendekkan)
SEC("fexit/io_submit_one")
int BPF_PROG(handle_io_submit_one_exit, struct kioctx *ioctx,
	     struct iocb *user_iocb, bool compat, int ret)
{
	struct iocb ib;
	unsigned long long cookie = (unsigned long long)user_iocb;
	unsigned long long emitted = 0;

	if (ret < 0) {
		bpf_map_delete_elem(&dio_inflight, &cookie);
		return 0;
	}

	bpf_probe_read_user(&ib, sizeof(ib), user_iocb);
	if (ib.aio_lio_opcode != IOCB_CMD_PWRITE &&
	    ib.aio_lio_opcode != IOCB_CMD_PWRITEV) {
		bpf_map_delete_elem(&dio_inflight, &cookie);
		return 0;
	}

	struct statediff_vfs_pending *p = get_scratch(SD_VFS_OP_DIO_SUBMIT);
	p->offset = ib.aio_offset;

	if (ib.aio_lio_opcode == IOCB_CMD_PWRITE) {
		unsigned int got = dio_emit_one(p, cookie, ib.aio_offset,
						(const void *)ib.aio_buf,
						ib.aio_nbytes);
		if ((unsigned long long)got != ib.aio_nbytes)
			goto abort;
		emitted = got;
	} else {
		struct dio_seg_ctx c = {
			.p = p, .iov = (const struct iovec *)ib.aio_buf,
			.cookie = cookie, .pos = ib.aio_offset,
		};
		unsigned int segs = (unsigned int)ib.aio_nbytes;
		bpf_loop(segs, dio_emit_seg, &c, 0);
		if (c.failed)
			goto abort;
		emitted = c.emitted;
	}

	dio_emit_control(SD_VFS_OP_DIO_SUBMIT_DONE, cookie, 0, emitted);
	return 0;

abort:
	bpf_map_delete_elem(&dio_inflight, &cookie);
	dio_emit_control(SD_VFS_OP_DIO_ABORT, cookie, -1, emitted);
	return 0;
}
Penjelasan

Di titik keluar io_submit_one, kernel sudah selesai meng-import IOCB dan buffer user (memory-nya sudah pasti ter-fault-in), sehingga bpf_probe_read_user(&ib, sizeof(ib), user_iocb) aman dipanggil di sini — kebalikan dari hook masuk.

ib.aio_lio_opcode — kode operasi asli permintaan AIO. Hanya IOCB_CMD_PWRITE (tulis satu buffer) dan IOCB_CMD_PWRITEV (tulis banyak buffer/iovec) yang diproses; operasi baca diabaikan di titik ini juga (walau completion-nya baru benar-benar disaring di hook aio_complete_rw).

Cabang IOCB_CMD_PWRITE memanggil dio_emit_one (mirip dio_emit_seg/potongan vfs_write: salin isi buffer ke event_scratch, kirim event DIO_SUBMIT). Cabang IOCB_CMD_PWRITEV memakai bpf_loop dengan dio_emit_seg — pola yang sama persis seperti writev_emit_seg di Bagian 8.2, hanya dengan tipe event DIO_SUBMIT.

Kalau semua segmen berhasil dikirim → dio_emit_control(SD_VFS_OP_DIO_SUBMIT_DONE, ...) menandai "staging untuk cookie ini selesai". Kalau ada yang gagal di tengah jalan (goto abort) → dio_emit_control(SD_VFS_OP_DIO_ABORT, ...) memberi tahu userspace capture untuk operasi ini gagal, dan cookie dihapus dari dio_inflight supaya completion nanti tidak menunggu cookie yang sudah dibatalkan.

SEC("fentry/aio_complete_rw")
int BPF_PROG(handle_aio_complete_rw, struct kiocb *kiocb, long res)
{
	unsigned long long cookie;

	if (!kiocb)
		return 0;
	cookie = BPF_CORE_READ((struct aio_kiocb *)kiocb, ki_res.obj);

	}

Penjelasan

aio_prep_rw() memasang aio_complete_rw sebagai fungsi ki_complete untuk semua operasi AIO, baca maupun tulis — hook ini terpasang di titik yang sama untuk keduanya, dan menyaring sendiri operasi tulis.

cookie = BPF_CORE_READ((struct aio_kiocb *)kiocb, ki_res.obj); — kernel sendiri yang menyimpan alamat user_iocb asli (cookie kita) ke field ini saat submit, jadi di sisi completion cookie itu bisa ditarik balik dari struct kernel, tanpa perlu membaca memory user sama sekali.

if (!bpf_map_lookup_elem(&dio_inflight, &cookie)) return 0; — kalau cookie ini tidak terdaftar (bukan operasi yang kita catat, atau sudah dihapus lewat abort), lewati.

if (!(BPF_CORE_READ(kiocb, ki_flags) & IOCB_WRITE)) { ...; return 0; } — ki_flags adalah field milik kernel (bukan IOCB user), jadi bisa dibaca aman di sini untuk membedakan baca vs tulis tanpa harus menyentuh memory user. Operasi baca dibuang di sini.

dio_emit_complete(kiocb, cookie, res) (fungsi terpisah, baris 1497–1530) membaca kiocb->ki_filp untuk resolve path (masih valid di titik ini), lalu mengirim event DIO_COMPLETE berisi hasil (res) dan identitas file.

Kenapa dibangun langsung di ring buffer, bukan lewat scratch?

Komentar sumber (baris 1492–1495): completion sebuah operasi O_DIRECT asinkron bisa terjadi di konteks softirq (interrupt), bukan konteks proses biasa. Memakai map scratch per-CPU yang sama dengan hook lain berisiko bentrok kalau sebuah hook konteks-proses sedang memakainya di CPU itu juga. dio_emit_complete karena itu hanya melakukan pembacaan kernel dan satu bpf_map_lookup_elem — semuanya aman dijalankan dari softirq — lalu menulis langsung ke slot ring buffer yang baru dipesan.

Ringkasan urutan event satu operasi DIO PWRITE 
io_submit(IOCB_CMD_PWRITE, iocb_addr=0x7f0012340000, ...)

1. fentry/io_submit_one   -> dio_inflight[0x7f0012340000] = 1
2. fexit/io_submit_one    -> DIO_SUBMIT (payload byte, cookie=0x7f0012340000)
                           -> DIO_SUBMIT_DONE (cookie=0x7f0012340000)
3. fentry/aio_complete_rw -> DIO_COMPLETE (cookie=0x7f0012340000, res=jumlah byte, path)
                           -> dio_inflight[0x7f0012340000] dihapus

Userspace memasangkan ketiga event ini lewat cookie yang sama,
baru mengubahnya jadi satu record WRITE di batch .sd.
